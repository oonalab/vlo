Getting started ​

In ten minutes you will have a durable workflow running on your laptop, with no Docker and no cloud account. Then you will kill the process and watch the run continue.

Vlo keeps long-running work alive through crashes and restarts. You write a workflow as a pure reducer, (state, event) → [state, commands], and Vlo saves each step in one database transaction. Between steps a run is only rows in a database, so there is nothing to lose when a process dies.

Building an agent? Do this page first, then go to agent-harness.md.

Install ​

sh
pnpm add @oona/vlo zod
  • Node ≥ 22.5 (the SQLite journal uses node:sqlite).
  • Zod 4 is a peer dependency. @google-cloud/storage is optional and only needed for a gcs:// blob store.
  • The vlo CLI ships with @oona/vlo (npx vlo …).

The smallest program ​

Two files in one directory. The config says where the code and the journal live; the workflow module exports a reducer.

ts
// vlo.config.ts
import { defineConfig } from "@oona/vlo";

export default defineConfig({
  workflows: ["*.workflow.ts"],
  profiles: {
    local: { journal: "sqlite://.vlo/dev.db", blob: "file://.vlo/blobs" },
  },
});
ts
// hello.workflow.ts
import { cmd, defineWorkflow } from "@oona/vlo";

export default defineWorkflow("hello", {
  init: (input: { name: string }) => ({ greeting: `hello, ${input.name}` }),
  on: {
    started: (state) => [state, [cmd.complete(state.greeting)]],
    task_done: (state) => [state, []],
  },
});

init builds the initial state from the run input. started is the first event every run receives; here it completes the run at once. task_done is required by the type even when the workflow never schedules a task.

Relative imports inside the config and the modules it points at need explicit file extensions (./activities.ts); the files are imported by Node, not bundled.

Run it ​

sh
npx vlo dev
  ✓ journal  sqlite:///home/me/app/.vlo/dev.db
  ✓ found 1 workflow   hello
  ✓ api      http://localhost:4100

vlo dev uses the local profile (or the only profile in the file), migrates the journal, loads every module the globs match and serves the HTTP API on port 4100. A warning about "no workers found" is expected here: this workflow has no activities. See cli.md for every flag.

Start a run ​

With curl:

sh
curl -s -X POST http://localhost:4100/v1/runs \
  -H 'content-type: application/json' \
  -d '{"workflow":"hello","input":{"name":"world"}}'
# {"run_id":"run_…"}

curl -s http://localhost:4100/v1/runs/run_…
# {"run_id":"run_…","workflow":"hello","status":"completed","output":"hello, world",…}

With the client (it lives in @oona/vlo/host):

ts
import { createClient } from "@oona/vlo/host";

const client = createClient({ baseUrl: "http://localhost:4100" });

const started = await client.start("hello", { name: "world" });
const done = await client.waitFor(started.run_id, "completed");
console.log(done.output); // "hello, world"

// Or follow the journal live over SSE until the run ends.
for await (const message of client.stream(started.run_id)) {
  if (message.type === "journal") console.log(message.seq, message.data.step_id);
  if (message.type === "end") console.log(message.data.status);
}

client.get(runId) returns the same run view as GET /v1/runs/{id}. The full route list is in http-api.md.

Add an activity and a worker ​

Real workflows do their non-deterministic work in activities, run by workers. The sequence helper compiles a list of phases into a reducer.

ts
// activities.ts
import { z } from "zod";
import { activity } from "@oona/vlo";

export const shout = activity("hello.shout", {
  input: z.object({ text: z.string() }),
  output: z.object({ upper: z.string() }),
});
ts
// shout.workflow.ts
import { defineWorkflow, sequence, step } from "@oona/vlo";
import { shout } from "./activities.ts";

export default defineWorkflow("shout", sequence([step(shout)]));
ts
// shout.worker.ts
import { defineWorker } from "@oona/vlo";

export default defineWorker({
  "hello.shout": (input: { text: string }) => ({ upper: input.text.toUpperCase() }),
});

Add the worker glob to the config and restart vlo dev:

ts
export default defineConfig({
  workflows: ["*.workflow.ts"],
  workers: ["*.worker.ts"],
  profiles: { local: { journal: "sqlite://.vlo/dev.db", blob: "file://.vlo/blobs" } },
});
ts
const started = await client.start("shout", { text: "hi" });
const done = await client.waitFor(started.run_id, "completed");
// done.output === { "hello.shout": { upper: "HI" } }

The worker runs in the same process as the engine. Moving it to another machine is a config change, not a code change: see activities-and-workers.md.

Kill it and watch it continue ​

This is the point of durable execution, and you can see it in a minute. The pipeline example plans three items, processes them two at a time, then waits for a person. Run it from a checkout of the repository:

sh
pnpm install                                               # once, from the repository root
cd examples && pnpm dev:pipeline                           # API on :4100

In a second terminal, start a run and look at it:

sh
curl -s -X POST localhost:4100/v1/runs -H 'content-type: application/json' \
  -d '{"workflow":"pipeline","input":{"n":3}}'            # → {"run_id":"run_…"}
curl -s localhost:4100/v1/runs/<run_id>                    # "status":"awaiting_signal"

The run is now waiting for an approval. Stop the host with Ctrl-C. No process is running for this run; it is a few rows in examples/pipeline/.vlo/pipeline.db.

Start the host again and approve:

sh
pnpm dev:pipeline
curl -s localhost:4100/v1/runs/<run_id>                    # still "awaiting_signal"
curl -s -X POST localhost:4100/v1/runs/<run_id>/signals/pipeline.approve \
  -H 'content-type: application/json' -d '{"by":"you"}'   # → {"delivered":true}
curl -s localhost:4100/v1/runs/<run_id>                    # "status":"completed"

The run finished with the work it did before the restart. Read its history, event by event:

sh
curl -s localhost:4100/v1/runs/<run_id>/events

What happened: on restart the host loaded the run's one checkpoint row, checked its hash and carried on. It did not re-run your workflow. A task that was in flight when the process died is handled the same way with one extra step: its lease lapses (60 seconds by default) and the retry policy starts a fresh attempt. See reliability.md.
