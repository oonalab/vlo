Journal ​

The journal is the only durable state Vlo has. It is the source of truth for every run and, because the tasks table doubles as an outbox with leases, it is also the queue. There is no broker: a transition commits its events, its checkpoint and its new task rows together, and the dispatcher picks the rows up on its next pass. Source: src/journal/**, src/blob/**.

Outbox and lease columns on tasks ​

status = 'scheduled' AND dispatched_at_ms IS NULL AND not_before_ms <= nowWaiting to be pushed or polled. A crash between commit and push loses nothing: the row is still here.

Text, not jsonb ​

Anything that is hashed or replayed — run_state.state, run_state.kernel_state, events.payload, runs.input, runs.output, tasks.input, schemas.retry_policy — is stored as text, byte-exact. jsonb rewrites key order and numeric lexemes, which would change the bytes the kernel hashes and break the re-fold check. Only runs.search, events.usage and tasks.retry_policy are jsonb on Postgres (plain TEXT on SQLite).

Postgres adapter ​

src/journal/postgres.ts, driver pg, options { schema?: string, max?: number }.

  • Own schema. Every table is created unqualified inside CREATE SCHEMA IF NOT EXISTS vlo. Nothing in the journal can reach public, so it coexists with whatever else uses the database.
  • Migrations on boot. host.start() (and therefore serve(), handler() and the first host.fetch) calls journal.migrate(). vlo doctor does the same unless --no-migrate is given. The migration lock is a transaction-scoped advisory lock on vlo:migrate, so several processes may boot at once.
  • Session-free. The adapter keeps no session state at all: no startup options, no session-level SET, no session advisory locks. Every read and every transaction is BEGIN · SET LOCAL search_path TO <schema> · statements · COMMIT on a pooled connection. Per-run serialisation is pg_advisory_xact_lock(hashtextextended($1, 0)) on the key vlo:run:<run_id>, released at commit. Claims use FOR UPDATE SKIP LOCKED, so concurrent dispatcher passes get disjoint rows.
  • Why it works behind transaction-mode poolers. PgBouncer in transaction mode, PlanetScale and Neon's poolers multiplex sessions and reject startup parameters. Because the journal never assumes the next statement lands on the same backend, and everything it sets is LOCAL to one transaction, it is correct behind any of them.
  • Placeholders are written once as ? and rewritten to $n for Postgres.

SQLite adapter ​

src/journal/sqlite.ts, built on node:sqlite (Node ≥ 22.5), no native dependency.

  • One file, one connection, one writer. A promise mutex owns the connection: a transaction holds it from BEGIN IMMEDIATE to COMMIT; reads queue behind it. BEGIN IMMEDIATE takes the write lock up front, which is what makes claims disjoint without SKIP LOCKED.
  • Pragmas on open: journal_mode = WAL, busy_timeout = 5000, foreign_keys = ON.
  • The directory of the file is created on demand, so vlo doctor and vlo serve work on a fresh checkout. sqlite://:memory: gives a throwaway journal for tests.
  • Share one SqliteJournal instance per process. Separate processes on the same file are serialised by SQLite's lock and busy_timeout.

Privileges the Postgres role needs ​

The first boot does two things in order: create the schema (vlo by default), then create the tables inside it. Each needs one privilege, and the two are on different objects:

StepNeedsGranted by
CREATE SCHEMA vloCREATE on the databaseGRANT CREATE ON DATABASE <db> TO <role>;
tables and indexes in vloCREATE on the schemaautomatic for the schema's owner; otherwise GRANT USAGE, CREATE ON SCHEMA vlo TO <role>;

Pick one of two setups:

  • Let the app own the schema (simplest). Grant CREATE on the database once. The app creates vlo on first boot, owns it, and needs nothing else afterwards. Steady-state runtime only needs USAGE on the schema and DML on its tables, which the owner has.
  • DBA-provisioned schema. If the role may not have database-level CREATE, have an admin run CREATE SCHEMA vlo AUTHORIZATION <role>; once. The host sees the schema and skips creation.

Do not mix them by creating the schema as a different role: the app is then not the owner and fails on the first table with permission denied for schema vlo until it also receives USAGE, CREATE on the schema.

Diagnostics, run as an admin on the same database the app connects to:

sql
SELECT usename, count(*) FROM pg_stat_activity WHERE usename LIKE '%' GROUP BY 1;  -- who is actually connected
SELECT has_database_privilege('<role>', current_database(), 'CREATE');             -- step 1
SELECT has_schema_privilege('<role>', 'vlo', 'CREATE');                            -- step 2
SELECT version FROM vlo.migrations ORDER BY 1;                                     -- what the boot achieved

Behind a pooler the login name can carry routing information (PlanetScale uses <role>.<branch>); the Postgres role is the part the pooler maps it to, which pg_stat_activity shows. Grant to that name. vlo doctor prints these remedies when a boot fails on either privilege.

Migrations ​

Migrations are SQL strings inlined as TypeScript modules, one per dialect and version, listed in MIGRATION_VERSIONS (src/journal/migrations.ts):

VersionAdds
0001_initEvery table above and its indexes.
0002_task_timeouttasks.timeout_ms and the tasks_timeout_idx partial index behind the timeout reaper.
0003_continued_toruns.continued_to, the forward link written when continue_as_new starts a successor.

The runner reads migrations, applies whatever is missing inside the caller's transaction and inserts the bookkeeping row. Postgres statements are IF NOT EXISTS and rerunnable; SQLite's ALTER TABLE … ADD COLUMN in 0002 and 0003 is guarded only by the migrations row, so do not delete that table on SQLite.

Blob stores ​

Anything over the inline limit — INLINE_LIMIT_BYTES, 256 KiB — leaves the journal and is stored content-addressed. The journal keeps a reference of the form blob://sha256/<64 hex> in the matching *_ref column (payload_ref, input_ref, output_ref, state_ref).

ts
interface BlobStore {
  /** Stores the bytes and returns their sha256, lowercase hex. Idempotent. */
  put(bytes: Uint8Array): Promise<string>;
  get(sha256Hex: string): Promise<Uint8Array>;
}

offloadIfOversized(store, text) returns the ref when the UTF-8 byte length exceeds the limit and null otherwise; readBlobText(store, ref) reads it back byte-exact. The kernel decides state_inline for the checkpoint; the host offloads the completion output the same way.

URLStoreNotes
file://<dir>FileBlobStore<dir>/<first two hex>/<sha256>; written to a temp file and renamed, so readers never see a partial blob. Default is file://.vlo/blobs; a relative directory resolves like a SQLite path (config directory from a profile, working directory when opened directly).
gcs://<bucket>[/<prefix>]GcsBlobStoreObject key <prefix>/<first two hex>/<sha256>. put checks existence first, so a retried offload uploads nothing. Needs the optional peer dependency @google-cloud/storage (^7). Credentials: Application Default Credentials, or GCP_SERVICE_ACCOUNT_KEY_BASE64 (base64 of a service-account JSON) where no metadata server exists.

openBlobStore(url) throws unsupported blob store url: … for any other scheme. vlo doctor writes a 1 KiB probe and checks that put returned its real sha256 and that get returned every byte.

JournalClosed ​

Every journal call made after close() rejects with JournalClosed (code: "journal_closed", exported from @oona/vlo/host). Shutdown is racy by nature — a worker reporting a result while the host stops — and this is the one recognisable error those late calls get instead of whatever the driver does to a closed handle. The dispatcher drops it silently as "shutting down" rather than emitting a warning.

The interface ​

Journal (src/journal/types.ts) is what the host talks to. Reads outside a transaction: readEvents, getRun, getState, getTask, listTasks, query, dueTimers, expiredLeases, expiredTimeouts. Everything that writes goes through transaction(fn) and a JournalTx: lockRun, createRun, applyTransition (the whole kernel write-set plus the child and successor run rows the host derives, atomically), the claim methods (claimUndispatchedTasks, claimCreatedRuns, claimClosedUnnotified, claimDueTimers), lease methods (markDispatched, deferDispatch, heartbeat), timer and signal methods, and the schema registry (upsertSchema, getSchema).

If you write another adapter, journalConformance from @oona/vlo/testing runs the same suite the two built-in journals pass: ordering, disjoint claims, hold expiry, terminal marks, idempotent appends. Point it at your Journal factory inside a Vitest describe.
